# 并发设计经验笔记（可复用版）

> 主题：从这次 Task Scheduler 实现中沉淀出的“可迁移并发方法论”

---

## 1. 先讲结论

- 并发代码看起来复杂，核心其实是：**状态机 + 协议 + 证据**。
- 好设计不是“写得巧”，而是先排除坏循环（忙等/死锁/漏通知），再做性能优化。
- 你这次最有价值的成长点：已经从“实现功能”转到“追问每个 wait/notify 的语义”。

---

## 2. 我在实战里最常用的 5 个技巧

### 技巧 1：先写状态机，再写代码

先定义线程状态（A 等批次、B 执行、C 等尾），再定义转移条件。  
代码只是在“翻译状态机”，不是靠临场拼凑。

**检查点**
- [ ] 每个状态有唯一职责
- [ ] 每个转移由明确条件触发
- [ ] 不存在“条件恒真导致自旋”路径

### 技巧 2：优先找“坏循环”

并发 Bug 的高发源头是坏循环，比如：

```text
回 A -> 谓词立即为真 -> 回 B 抢空 -> 再回 A ...
```

这个循环会造成 CPU 忙等，但看起来程序“还在跑”。  
你的 C 段就是专门切断这个坏循环的。

**检查点**
- [ ] 是否存在“无有效工作但持续占 CPU”路径
- [ ] wait 谓词是否会在错误状态下恒真

### 技巧 3：通知必须分工（谁叫醒谁）

不要把所有事件混在一个通知里：

- `cv_done.notify_one()`：只负责唤醒主线程（`run()` 返回）
- `cv_work.notify_all()`：只负责唤醒 worker（A/C 段切换）

通知职责清晰，才不容易漏通知或误唤醒。

**检查点**
- [ ] 每个 notify 都能回答“唤醒对象是谁”
- [ ] wait 条件与 notify 事件一一对应

### 技巧 4：严格区分“号领完”和“任务做完”

- `next_task_id_ >= n`：只是“任务分配完”
- `remaining_tasks == 0`：才是“任务执行完”

这是线程池最容易混淆的一点。  
你现在的 C 段 + 最后任务收尾，本质是在补这条语义鸿沟。

### 技巧 5：先正确性闭环，再性能优化

顺序固定：
1. 无 data race / 无死锁 / 无漏通知
2. 再做 chunk、主线程参与、内存序微调

“快但偶发挂死”的实现，在工程上是不可用的。

## 3. 这次 Task Scheduler 的关键经验

### 经验 A：C 段不是“多余等待”，是“防空转屏障”

当 worker 抢空号但批次未结束时，若直接回 A，会出现 A/B 忙等环。  
C 段 `wait(stop || !batch_active)` 强制线程睡到批次结束，避免空转。

### 经验 B：最后一个任务要承担“收尾职责”

最后完成任务的 worker 负责：
- `batch_active=false`
- `notify_one(cv_done)` 让 `run()` 返回
- `notify_all(cv_work)` 让 C 段线程脱离尾等待

这叫“最后完成者协议”（Last Finisher Protocol）。

### 经验 C：发布协议必须原子化

`run()` 里 batch 元数据（runnable、计数器、active 标志）需要在同一临界区发布，再通知 worker。  
否则会出现“读到半初始化状态”的竞态。

## 4. 可直接复用的一页设计卡（每次写并发模块都填）

1. **API 契约**
   - 返回时保证什么完成条件？
2. **共享状态**
   - 谁写、谁读、在哪个锁域里？
3. **等待条件**
   - 每个 wait 谓词是什么？
4. **通知拓扑**
   - 每个 notify 唤醒谁？
5. **最后完成者协议**
   - 谁负责收尾与终态切换？
6. **坏循环排查**
   - 是否存在“无工作高 CPU”路径？
7. **析构协议**
   - 是否 `stop -> notify -> join` 闭合？

## 5. 最小复盘模板（下次继续用）

1. 这轮目标是否达成（1-2 句）
2. 最大误区是什么（最多 3 条）

4. 最小修正动作是什么

## 6. 给未来自己的提醒
