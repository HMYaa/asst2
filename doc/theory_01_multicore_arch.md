# 理论 01：现代多核处理器架构

> 一句话：理解你写的多线程代码运行在什么样的硬件上，以及硬件的哪些特性决定了并行程序的性能上限。

## 为什么你需要学这个

Lab 2 要求你在多核 CPU 上实现一个 Task Scheduler。你做的每一个设计决策——线程创建多少个、任务怎么分配、用自旋还是睡眠——最终都由底层硬件特性决定收益。不理解硬件，优化就是盲人摸象。

Lab 2 的测试环境是 AWS c7g.4xlarge（16 个执行上下文），你需要知道这 16 个上下文是怎么来的，以及它们之间共享了什么、竞争了什么。

## 核心概念

---

### 概念 1：多核处理器（Multi-core Processor）

**定义**

多核处理器是在单个芯片（die）上集成多个独立的处理器核心（core）的微处理器。每个核心拥有独立的取指、译码、执行单元和 L1/L2 缓存，能够独立执行指令流。多核间通过片上互连网络（on-chip interconnect）和共享的末级缓存（Last Level Cache, LLC）进行通信。

**直觉**

想象一个快递分拣中心：

```
单核时代：1 个分拣员，速度再快也就那么快（频率墙）
多核时代：8 个分拣员同时干活，总吞吐量翻倍
         但他们共享一条传送带（内存总线），抢传送带时会堵
```

CPU 从 2005 年左右开始走多核路线，原因很简单：单核频率从 3GHz 往上提，功耗会以立方关系增长（P ∝ f³），芯片会烧掉。所以改成多个低频核心并行工作，总功耗可控，总算力提升。

**机制**

一个典型的现代多核处理器（如 AWS Graviton3，Lab 2 测试用的 c7g.4xlarge）：

```
┌─────────────────────────────────────────────────┐
│                    芯片（Die）                    │
│                                                   │
│  ┌──────┐  ┌──────┐  ┌──────┐  ┌──────┐         │
│  │Core 0│  │Core 1│  │Core 2│  │Core 3│  ...×16 │
│  │ L1-I │  │ L1-I │  │ L1-I │  │ L1-I │         │
│  │ L1-D │  │ L1-D │  │ L1-D │  │ L1-D │         │
│  │  L2  │  │  L2  │  │  L2  │  │  L2  │         │
│  └──┬───┘  └──┬───┘  └──┬───┘  └──┬───┘         │
│     └─────────┴─────────┴─────────┘              │
│                    │                              │
│           ┌───────┴────────┐                      │
│           │  L3 共享缓存     │                      │
│           │  (Last Level    │                      │
│           │   Cache, LLC)   │                      │
│           └───────┬────────┘                      │
│                   │                               │
└───────────────────┼───────────────────────────────┘
                    │ 内存总线
              ┌─────┴─────┐
              │   DRAM     │
              │  主存       │
              └───────────┘
```

关键参数（数量级感知）：

| 层级 | 容量 | 延迟 | 带宽 |
|------|------|------|------|
| L1 Cache | 32-64 KB/核 | ~1 ns (4 cycles) | ~TB/s |
| L2 Cache | 256 KB - 1 MB/核 | ~3-10 ns | ~数百 GB/s |
| L3 Cache（共享）| 16-64 MB/芯片 | ~10-30 ns | ~数百 GB/s |
| DRAM | 16-256 GB | ~50-100 ns | ~50-100 GB/s |

**关键洞察**：L1 到 DRAM 的延迟差了 **50-100 倍**。你的程序是否能命中 cache，决定了性能的量级。

**在 Lab 2 中的体现**

Lab 2 的测试机是 AWS c7g.4xlarge：16 核 ARM (Graviton3)，无超线程，每个核是一个独立执行上下文。

```bash
# runtasks：part_a/ 或 part_b/ 下 make 编译出的可执行文件（Makefile 中 APP_NAME=runtasks）
# 用法：在 part_a 或 part_b 目录下执行 make，然后 ./runtasks -n 16 mandelbrot_chunked
./runtasks -n 16 mandelbrot_chunked
```

当 16 个 Worker 线程竞争同一个 `atomic<int> next_task_id_` 时，这个变量在 16 个核的 L1 cache 之间反复失效和重新加载。每次 `fetch_add` 都可能触发 ~10-30 ns 的 L3 访问延迟，而不是 ~1 ns 的 L1。这就是为什么 Spinning 版在轻量任务上的开销来源。

### 概念 2：超线程 / 同时多线程（SMT, Simultaneous Multithreading）

**定义**

同时多线程（SMT）是一种在单个物理核心上通过维护多套架构状态（寄存器文件、程序计数器等）来同时执行多个硬件线程的技术。多个线程共享该核心的执行单元（ALU、FPU）和缓存资源。Intel 的商品名为 Hyper-Threading。

**直觉**

```
没有 SMT：
  一个厨师（核心）在烤面包时，等烤箱（内存访问）的 50ns 里干坐着

有 SMT：
  同一个厨师，烤面包时切换去切菜（另一个线程），烤箱响了再切回来
  厨房（执行单元）同一时刻只有一个人在用，但两道菜的总完成时间缩短了
```

SMT 不是真正的"两个核"，它是**一个核心假装自己是两个**。好处是利用一个线程等待内存时的空闲周期；坏处是两个线程争抢同一套 ALU 和 cache，各自性能都比独占时低。

**机制**

```
物理核心 0 内部：
┌──────────────────────────────────┐
│     硬件线程 0   │   硬件线程 1    │  ← 两套寄存器/PC
│     (逻辑核 0)   │   (逻辑核 1)    │
│         ↓        │        ↓        │
│  ┌──────┴────────┴────────┐      │
│  │  共享的执行单元（ALU/FPU）│      │  ← 竞争资源
│  │  共享的 L1/L2 Cache     │      │
│  └─────────────────────────┘      │
└──────────────────────────────────┘

OS 视角：看到 2 个"CPU"，实际是 1 个物理核的 2 个硬件线程
```

典型加速比：SMT 开启后，单核吞吐提升约 **20-30%**（远不是 2x）。

**在 Lab 2 中的体现**

AWS c7g.4xlarge 使用 ARM Graviton3，**没有 SMT**。所以 16 核就是 16 个物理核，每个核是一个独立执行上下文。

这意味着：
- `num_threads = 16` 时，每个 Worker 线程独占一个物理核心，不存在 SMT 共享资源的竞争
- 如果你在自己的 Intel 笔记本（通常有超线程）上测试，`-n 8` 在 4 核 8 线程的机器上，后 4 个线程和前 4 个共享物理核，性能不会线性增长

### 概念 3：内存层次结构与延迟鸿沟

**定义**

内存层次结构（Memory Hierarchy）是计算机系统中按照访问速度和容量分层组织存储的架构设计。越靠近处理器核心的存储层级速度越快、容量越小、成本越高。程序性能严重依赖数据访问的**局部性（Locality）**——即数据是否在快速的上层缓存中命中。

**直觉**

```
层级       类比                  访问时间     你在代码中触发的操作
─────────────────────────────────────────────────────────────
L1 cache   你手边的便签纸          ~1 ns      读一个已经在循环中反复用的变量
L2 cache   你桌上的文件夹          ~5 ns      读一个最近访问过的数组元素
L3 cache   办公室的文件柜          ~20 ns     另一个核刚写过的 atomic 变量
DRAM       图书馆的书架            ~80 ns     首次访问一个大数组的远端元素
磁盘/SSD   从外地调档案            ~10 μs+    本课程不涉及
```

**关键数字**：L1 命中 vs DRAM 访问 = **1 ns vs 80 ns = 80 倍延迟差距**。

**机制**

**Cache Line（缓存行）** 是缓存和内存之间传输数据的最小单位，通常为 **64 字节**。

当 CPU 访问地址 A：
1. 检查 L1 cache → 命中（hit）？直接返回，~1 ns
2. L1 未命中 → 检查 L2 → 命中？返回，~5 ns
3. L2 未命中 → 检查 L3 → 命中？返回，~20 ns
4. L3 未命中 → 访问 DRAM，~80 ns，同时将包含 A 的整个 64-byte cache line 加载到 L1/L2/L3

两种局部性：
- **时间局部性（Temporal Locality）**：刚访问过的数据很快会再次被访问。例如：循环计数器 `i`。
- **空间局部性（Spatial Locality）**：访问了地址 A，很快会访问 A 附近的地址。例如：遍历数组 `arr[i], arr[i+1], ...`。因为 cache line 是 64 字节一起加载的，所以 `arr[0]` 命中后 `arr[1]` 到 `arr[15]`（假设 int=4 bytes）都已经在 cache 中了。

**在 Lab 2 中的体现**

Lab 2 不同测试用例的性能瓶颈不同：

| 测试 | 主要瓶颈 | 原因 |
|------|---------|------|
| `recursive_fibonacci` | 计算（CPU-bound） | 纯递归计算，数据极少，全在 L1 |
| `ping_pong_equal` | 内存（Memory-bound） | 在两个大 buffer 间复制数据，缓存容量不够 |
| `super_super_light` | 调度开销 | 任务本身几乎不做事，线程同步成为主要耗时 |

理解这个表，你就知道为什么同一种线程池实现，在不同测试上的加速比差异巨大。

> **RDMA 映射**：RDMA 的核心设计哲学就是围绕内存层次优化的——DMA 引擎直接搬运数据到用户态内存（绕过 CPU cache），注册内存区域（MR）让 RNIC 可以直接访问物理地址（绕过页表），这些都是为了在"延迟鸿沟"中找到最短路径。

### 概念 4：指令级并行（ILP）与频率墙

**定义**

指令级并行（Instruction-Level Parallelism, ILP）是指单个程序中不存在数据依赖或控制依赖的指令可以被处理器同时执行的程度。现代超标量（superscalar）处理器通过乱序执行（Out-of-Order Execution）、分支预测（Branch Prediction）和流水线（Pipeline）来挖掘 ILP。频率墙（Frequency Wall）是指由于功耗与频率的超线性关系（P ∝ V² × f，V 随 f 增长），单核频率无法持续提升的物理限制。

**直觉**

```
2000 年前：CPU 每年提频 → 软件不改也能变快（"免费午餐"）
2005 年后：频率卡在 3-4 GHz → 只能加核数来提总算力（"午餐不免费了"）

你的代码不再能靠"等新 CPU"变快，你必须显式地写并行程序。
这就是 Lab 2 存在的根本原因。
```

**机制**

功耗公式（CMOS 动态功耗）：

```
P_dynamic = C × V² × f

C = 电容负载（与晶体管数量成正比）
V = 电压（与频率正相关，提频需要提压）
f = 时钟频率

因为 V ∝ f（近似），所以 P ∝ f³

实际数字：
  3 GHz → 4 GHz（频率提 33%）
  功耗增加约 33%³ ≈ 2.4 倍
  性能提升约 33%
  → 性能/功耗比下降近 2 倍，极不划算
```

这就是为什么 Intel/AMD/ARM 都在 2005 年后转向多核：
- 2 个 2 GHz 核心 vs 1 个 4 GHz 核心
- 功耗：2 × (2/4)³ = 2 × 0.125 = 0.25 → 功耗只有单核的 **1/4**
- 算力：2 × 0.5 = 1.0 → 总算力相当（理论上）
- 前提：**你的程序能利用两个核**，否则只有 0.5 的算力

**在 Lab 2 中的体现**

这解释了 Lab 2 的一个核心现象：

```
串行版（Serial）：只跑在 1 个核上，100% 利用率，但只有 1/16 的总算力
并行版（16 线程）：理想情况下 16 倍加速
实际情况：由于调度开销、内存竞争、负载不均，加速比 < 16

你的目标：让加速比尽可能接近 16
```

### 概念 5：SIMD（简要了解）

**定义**

单指令多数据（Single Instruction Multiple Data, SIMD）是一种数据级并行技术，处理器使用一条指令同时对多个数据元素执行相同的操作。现代 CPU 支持 128 位（SSE）、256 位（AVX2）或 512 位（AVX-512）的 SIMD 寄存器。

**直觉**

```
标量：一次加法处理 1 个 float        → 1 条指令 = 1 个结果
SIMD：一次加法处理 8 个 float（AVX2）→ 1 条指令 = 8 个结果
```

**在 Lab 2 中的体现**

Lab 2 不涉及显式 SIMD 编程（那是 Lab 1/ISPC 的内容）。但了解 SIMD 的存在有助于理解：编译器可能自动向量化你的 `runTask` 内部循环，这会影响单个 task 的执行时间，间接影响线程池的调度粒度决策。

**结论：你知道它存在即可，Lab 2 不需要手动使用。**

## 关键结论

- [ ] 现代 CPU 是多核的，单核频率已触顶（~3-4 GHz），并行是唯一的出路
- [ ] 内存层次的延迟鸿沟（L1: 1ns → DRAM: 80ns）决定了数据放在哪里比算得有多快更重要
- [ ] Cache Line 是 64 字节，这个数字在后续 False Sharing 分析中至关重要
- [ ] AWS c7g.4xlarge = 16 物理核心，无 SMT，所以 `num_threads=16` 就是硬件上限
- [ ] Lab 2 不同测试的瓶颈不同：有的是计算密集，有的是内存密集，有的是调度开销主导

**[思考题 1]**
16 个 Worker 线程同时对同一个 `std::atomic<int>` 执行 `fetch_add(1)`，每次操作的延迟大约是多少？是 L1 级别（~1ns）还是 L3 级别（~20ns）？为什么？

<details>
<summary>参考思路</summary>

是 **L3 级别（~20ns 或更高）**。

原因：`fetch_add` 是 read-modify-write 操作，需要获取该 cache line 的独占权（MESI 中的 Exclusive/Modified 状态）。当 16 个核同时竞争同一个 cache line 时，每次操作都需要通过缓存一致性协议使其他核的副本失效，然后从 L3（或直接从其他核的 L1/L2）获取最新值。这个过程的延迟是 L3 级别的。

这就是为什么高并发 `atomic` 操作在轻量任务场景下成为性能瓶颈——Spinning 版线程池中，16 个 Worker 争抢 `next_task_id_` 的开销可能比 task 本身的执行时间还长。
</details>

**[思考题 2]**
假设 Lab 2 的某个测试中，每个 task 的执行时间约为 10 μs，总共有 1000 个 task，使用 16 个线程。理想加速比是多少？如果线程创建和销毁的总开销是 500 μs（ParallelSpawn 版），实际加速比大约是多少？

<details>
<summary>参考思路</summary>

理想情况：
- 串行耗时 = 1000 × 10 μs = 10,000 μs
- 理想并行耗时 = 10,000 / 16 = 625 μs
- 理想加速比 = 16x

ParallelSpawn 版实际：
- 并行耗时 = 625 μs（计算）+ 500 μs（线程创建销毁开销）= 1,125 μs
- 实际加速比 = 10,000 / 1,125 ≈ **8.9x**

线程创建开销吃掉了近一半的并行收益。如果 task 更轻量（比如 1 μs），情况更糟：
- 串行 = 1,000 μs，并行 = 62.5 + 500 = 562.5 μs
- 加速比 = 1,000 / 562.5 ≈ **1.8x**（几乎没有加速）

这就是为什么需要线程池（ThreadPool）：消除重复创建线程的开销。
</details>

**[代码预测题]**
以下代码有什么问题？预测在 16 线程运行 10000 次后，`counter` 的值是否等于 160000？

```cpp
int counter = 0;                    // 注意：不是 atomic
std::mutex mtx;

void worker() {
    for (int i = 0; i < 10000; i++) {
        mtx.lock();
        counter++;
        mtx.unlock();
    }
}
// 启动 16 个线程，每个线程执行 worker()
```

<details>
<summary>分析</summary>

**counter 最终等于 160000。代码是正确的。**

虽然 `counter` 不是 `atomic`，但每次 `counter++` 都在 `mtx` 的保护下执行。mutex 的 lock/unlock 提供了足够的同步保证（happens-before 关系），确保一个线程 unlock 后写入的值对下一个 lock 的线程可见。

但这段代码的**性能很差**：每次 `++` 都要经过 lock/unlock，16 个线程串行排队。如果改用 `std::atomic<int> counter` 配合 `fetch_add(1)`，可以去掉 mutex，性能会好很多——因为 atomic 的 fetch_add 底层是一条 CPU 指令（如 `lock xadd`），比 mutex 的内核调用开销小一个量级。

这就是 Lab 2 中推荐用 `atomic<int>` 做 task_id 计数器而非 `mutex + int` 的原因。
</details>
