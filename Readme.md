## 概述

大家都喜欢快速完成任务，而在这个实验中，我们要让你做的就是这件事！你将实现一个 C++ 库，以便在多核 CPU 上尽可能高效地执行应用程序提供的任务。 

在实验的第一部分，你将实现一个支持批量（数据并行）启动同一任务的多个实例的任务执行库版本。这项功能类似于你在实验 1 中用来跨核心并行化代码的 ISPC 任务启动行为。 

在实验的第二部分，你将扩展你的任务运行时系统，以执行更复杂的**任务图（task graphs）**，其中任务的执行可能依赖于其他任务产生的结果。这些依赖关系限制了哪些任务可以被你的任务调度系统安全地并行运行。

在并行机器上调度执行数据并行的任务图，是许多流行并行运行时系统的一个特性，从广受欢迎的 Thread Building Blocks (TBB) 库，到 Apache Spark，再到现代深度学习框架（如 PyTorch 和 TensorFlow）。本实验将要求你：

- 使用线程池管理任务执行
- 使用互斥锁和条件变量等同步原语来编排工作线程的执行
- 实现一个反映任务图定义的依赖关系的任务调度器
- 理解工作负载特征，以做出高效的任务调度决策

我们建议复习我们的 C++同步教程，以获取有关 C++ 标准库中同步原语的更多信息。此外，查看测试用例描述以了解你的库将支持的工作负载类型可能会有所帮助。

## A 部分：同步批量任务启动

在实验 1 中，你使用了 ISPC 的任务启动原语来启动 N 个 ISPC 任务实例（`launch[N] myISPCFunction()`）。在本实验的第一部分，你将在你的任务执行库中实现类似的功能。

为了开始工作，请熟悉 `itasksys.h` 中 `ITaskSystem` 的定义。这个抽象类定义了你的任务执行系统的接口。该接口包含一个 `run()` 方法，其签名如下：

```cpp
virtual void run(IRunnable* runnable, int num_total_tasks) = 0;
```

`run()` 将执行指定任务的 `num_total_tasks` 个实例。由于这单个函数调用会导致许多任务被执行，我们将每次对 `run()` 的调用称为一次**批量任务启动（bulk task launch）**。

`tasksys.cpp` 中的初始代码包含了一个正确但串行的 `TaskSystemSerial::run()` 实现，它作为示例展示了任务系统如何使用 `IRunnable` 接口来执行批量任务启动。（`IRunnable` 的定义在 `itasksys.h` 中）请注意，在每次调用 `IRunnable::runTask()` 时，任务系统如何为任务提供当前的独立标识符（一个介于 0 到 `num_total_tasks` 之间的整数），以及批量任务启动中的总任务数。任务的实现将使用这些参数来决定它应该执行什么工作。

`run()` 的一个重要细节是，它必须相对于调用线程**同步**执行任务。换句话说，当对 `run()` 的调用返回时，应用程序可以确保任务系统已经完成了该次批量启动中的**所有任务**。初始代码中提供的 `run()` 串行实现会在调用线程上执行所有任务，从而满足了这一要求。

#### 步骤 1：转向并行任务系统

**在这一步，请实现 `TaskSystemParallelSpawn` 类。**

初始代码在 `TaskSystemSerial` 中为你提供了一个任务系统的串行工作实现。在本实验的这一步中，你将扩展初始代码，以并行方式执行批量任务启动。

- 本着“先做最简单的事”的精神，我们建议你在 `run()` 的开头生成工作线程，并在 `run()` 返回之前在主线程中联结（join）这些线程。这将是一个正确的实现，但它会因为频繁创建线程而产生巨大的开销。
- 你将如何将任务分配给你的工作线程？你应该考虑将任务静态分配还是动态分配给线程？
- 是否有需要保护的共享变量（任务执行系统的内部状态），以防止多个线程同时访问？

#### 步骤 2：使用线程池避免频繁创建线程

**在这一步，请实现 `TaskSystemParallelThreadPoolSpinning` 类。**

你在步骤 1 中的实现会由于在每次调用 `run()` 时创建线程而产生开销。当计算任务的成本很低时，这种开销尤为明显。此时，我们建议你转向“线程池”实现，让你的任务执行系统预先创建所有工作线程（例如，在 `TaskSystem` 构造期间，或在第一次调用 `run()` 时）。

- 作为初始实现，我们建议你将工作线程设计为连续循环，始终检查是否有更多工作要做。（线程进入 while 循环直到条件为真，通常被称为“自旋（spinning）”）。工作线程如何确定有工作要做？
- 现在要确保 `run()` 实现所需的同步行为并非易事。你需要如何修改 `run()` 的实现，以确定批量任务启动中的所有任务都已完成？

#### 步骤 3：在无事可做时让线程睡眠

**在这一步，请实现 `TaskSystemParallelThreadPoolSleeping` 类。**

步骤 2 实现的缺点之一是，线程在“自旋”等待要做的事情时，会占用 CPU 核心的执行资源。例如，工作线程可能会循环等待新任务的到来。另一个例子是，主线程可能会循环等待工作线程完成所有任务，以便它能从 `run()` 调用中返回。这会损害性能，因为 CPU 资源被用来运行这些线程，即使这些线程并没有做有用的工作。在实验的这一部分，我们希望你通过让线程进入睡眠状态直到它们等待的条件被满足，来提高任务系统的效率。

- 你的实现可以选择使用条件变量（condition variables）来实现这种行为。条件变量是一种同步原语，它使线程能够在等待条件成立时睡眠（并且不占用 CPU 处理资源）。其他线程会“发出信号（signal）”唤醒等待的线程，以查看它们等待的条件是否已经满足。例如，如果没有工作要做，你的工作线程可以进入睡眠状态（这样它们就不会抢占试图做有用工作的线程的 CPU 资源）。另一个例子，调用 `run()` 的主应用程序线程可能希望在等待工作线程完成批量任务启动中的所有任务时进入睡眠状态。（否则，自旋的主线程将抢占工作线程的 CPU 资源！）
- 你在本部分实验中的实现可能会遇到棘手的竞态条件（race conditions）。你需要考虑线程行为的许多可能交错方式。
- 你可能需要考虑编写额外的测试用例来检验你的系统。**实验初始代码包含了评分脚本用于给你的代码性能打分的工作负载，但我们也将使用我们在初始代码中未提供的更广泛的工作负载来测试你的实现的正确性！**

## B 部分：支持任务图的执行

在实验的 B 部分，你将扩展你在 A 部分中实现的任务系统，以支持可能依赖于先前任务的任务的异步启动。这些任务间的依赖关系产生了你的任务执行库必须遵守的调度约束。`ITaskSystem` 接口有一个额外的方法：

```cpp
virtual TaskID runAsyncWithDeps(IRunnable* runnable, int num_total_tasks, const std::vector<TaskID>& deps) = 0;
```

`runAsyncWithDeps()` 与 `run()` 类似，它也用于执行 `num_total_tasks` 个任务的批量启动。然而，它在许多方面与 `run()` 不同...

#### 异步任务启动

首先，使用 `runAsyncWithDeps()` 创建的任务由任务系统相对于调用线程**异步**执行。这意味着 `runAsyncWithDeps()` 应该**立即**返回给调用者，即使任务尚未完成执行。该方法返回与此批量任务启动相关的唯一标识符。

调用线程可以通过调用 `sync()` 来确定批量任务启动实际完成的时间。

```cpp
virtual void sync() = 0;
```

`sync()` **只有在与所有先前的批量任务启动相关的任务都已完成时，才会返回给调用者。**

如注释所述，在调用线程调用 `sync()` 之前，不能保证来自先前对 `runAsyncWithDeps()` 调用的任务已经完成。准确地说，`runAsyncWithDeps()` 告诉你的任务系统执行新的批量任务启动，但你的实现可以灵活地在下一次调用 `sync()` 之前的任何时间执行这些任务。请注意，此规范意味着不保证你的实现在开始执行 `launchB` 中的任务之前执行 `launchA` 中的任务！

#### 支持显式依赖

`runAsyncWithDeps()` 的第二个关键细节是它的第三个参数：一个 `TaskID` 标识符的向量，这些标识符必须指向之前使用 `runAsyncWithDeps()` 进行的批量任务启动。这个向量指定了当前批量任务启动中的任务依赖于哪些先前的任务。**因此，在依赖向量中给出的所有启动的任务完成之前，你的任务运行时不能开始执行当前批量启动中的任何任务！**

如果 `launchB` 和 `launchC` 依赖于 `launchA`，且 `launchD` 依赖于 `launchB` 和 `launchC`：虽然你的任务运行时可以按任何顺序（包括并行）处理与 `launchB` 和 `launchC` 相关的任务，但这些启动中的所有任务必须在 `launchA` 中的任务完成后才能开始执行，并且它们必须在你的运行时开始执行 `launchD` 中的任何任务之前完成。

我们可以将这些依赖关系可视化为一个**任务图（task graph）**。任务图是一个有向无环图 (DAG)，其中图中的节点对应于批量任务启动，从节点 X 到节点 Y 的边表示 Y 依赖于 X 的输出。 

请注意，如果你在一台具有八个执行上下文的 Myth 机器上运行该示例，那么并行调度 `launchB` 和 `launchC` 的任务的能力可能会非常有用，因为仅靠单个批量任务启动都不足以充分利用机器的所有执行资源。

#### 代码提交

我们要求你在压缩文件中提交源文件。你可以创建一个目录（例如 `asst2_submission`）包含子目录 `part_a` 和 `part_b`，通过运行 `tar -czvf asst2.tar.gz asst2_submission` 压缩并上传至 Gradescope 上的 *Assignment 2 (Code)* 作业中。

在提交之前，请确保所有代码都可以编译并运行！我们应该能够将这些文件放入干净的初始代码树中，输入 `make`，然后在没有手动干预的情况下执行。我们的评分脚本将运行检查器代码以确定性能得分，并将在*截止日期之后*在其他未提供的应用程序上运行以进一步测试正确性！

#### 实验报告提交

请向 Gradescope 上的 *Assignment 2 (Write-up)* 提交一份简短的实验报告，解决以下问题：

1. 描述你的任务系统实现（1页即可）。请确保解决了以下问题：
  - 你是如何决定管理线程的？（例如，你是否实现了线程池？）
    - 你的系统是如何将任务分配给工作线程的？静态还是动态分配？
    - 在 B 部分中，你是如何跟踪依赖关系以确保任务图的正确执行的？
2. 在 A 部分中，为什么更简单的任务系统实现有时性能与更高级的实现一样好，甚至更好？举例说明在什么情况下顺序任务系统实现表现最佳及其原因。在什么情况下“每次启动都生成线程”的实现表现与使用线程池一样好？什么时候不是这样？
3. 描述一个你为本实验实现的测试。这个测试做什么，旨在检查什么，你是如何验证解决方案在该测试中表现良好的？这个测试结果是否促使你更改了实现？
