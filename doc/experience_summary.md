# CS149 Lab 2 实战复盘：错误经验与修正笔记

## 一、ThreadPoolSpinning 早期实现中的典型误区

### 误区 1：把 stop 理解成“立刻停机”，而不是“安全退出协议”的一部分

**当时的错误想法**
- 只要析构时把 `stop=true`，worker 线程看到后直接退出就可以。
- 认为线程池销毁只需要考虑“线程能停下来”，不用考虑“队列里是否还有未处理任务”。

**为什么这是错误经验**
- 在线程池设计里，`stop` 不是单纯的“断电开关”，而是退出协议的一部分。
- 如果 worker 的退出条件只是 `stop == true`，那么队列里可能还有残留任务却没人处理。
- 更稳妥的语义应该是：**当 stop 为真且队列为空时，worker 才退出**。

**修正后的认识**
- 析构的关键不是“尽快停”，而是“退出语义是否自洽”。
- 正确问题应该问：析构到底要求“立即停机”还是“做完已接收任务再停机”？
- 在这类教学实验中，通常更稳健的设计是后者。

**以后遇到类似问题时提醒自己**
- 先定义线程退出条件，再写 `stop`。
- 任何 `stop` / `shutdown` 标志，都要和“队列是否为空”“是否还有 in-flight work”一起思考。

---

### 误区 2：没有严格区分“锁内操作”和“锁外操作”

**当时的错误想法**
- 只关注“怎么拿到任务”，对“什么时候必须立刻释放锁”认识还不够敏感。
- 容易把“检查队列 / 取任务 / 执行任务”混成一段连续逻辑来想。

**为什么这是错误经验**
- 锁的职责只是保护共享状态，而不是包住整个任务执行过程。
- 如果拿着锁去执行 `task()` / `runTask()`，其他 worker 就无法继续取任务，线程池会退化成串行瓶颈。
- 如果空队列时还不释放锁就 `_mm_pause()`，那更糟，等于空转时还霸占临界区。

**修正后的认识**
- **锁内只做共享数据结构操作，锁外做真正计算。**
- 在这个实验里，锁应该只保护：
  - 队列是否为空
  - pop / push
  - 可能的退出判定
- `runnable->runTask(...)` 必须放在锁外。

**以后遇到类似问题时提醒自己**
- 每次写临界区时都问自己一句：
  - “这段逻辑真的是在访问共享状态吗？”
  - “如果拿着锁执行这一步，会不会让别的线程没法前进？”

### 误区 3：把 `has_task` 写成跨轮次残留状态

**当时的错误想法**
- 认为 `has_task` 初始化一次就够了，只要之前取到过任务，就继续沿用这个变量。
- 没把它当作“本轮循环是否成功取到新任务”的局部状态来处理。

**为什么这是错误经验**
- `has_task` 如果不在每轮循环开始时重置，那么上一轮取到任务后，它会一直保持 `true`。
- 一旦下一轮队列空了但线程又没退出，代码就可能重复执行上一轮留下来的旧 `task`。
- 这是**严重正确性 bug**，会导致任务重复执行，而不是单纯性能差。

**修正后的认识**
- `has_task` 的语义必须是：**当前这一轮是否成功拿到了一个新任务**。
- 任何这种“本轮有效”的标志，都应该在循环顶部重置。

**以后遇到类似问题时提醒自己**
- 审查循环变量时，先判断它是：
  - 批次状态？
  - 线程长期状态？
  - 还是单轮临时状态？
- 单轮状态必须单轮初始化，不能残留到下一轮。

## 二、性能分析中的典型误区

### 误区 4：误以为“线程数越多，性能一定越好”

**当时的错误想法**
- 看到并行实现开始加速后，直觉上以为继续增加线程数会继续变快。
- 默认把线程数增长等价成“更多算力”。

**为什么这是错误经验**
- 并发程序的性能不只由计算量决定，还受调度开销、锁竞争、cache coherence、上下文切换等影响。
- 对 `super_light` 这种极轻任务，真正工作量非常小，调度器自身的开销会迅速成为主导。
- 所以线程数增加到一定程度后，新增线程带来的不是收益，而是更多 contention。

**这次实验中的直接证据**
- 2 线程和 8 线程时，`Parallel + Thread Pool + Spin` 有明显收益。
- 到 16 线程和 32 线程时，性能反而恶化，甚至出现断崖式下降。
- 这说明系统已经从 **compute-bound** 转成 **scheduler-contention-bound**。

**修正后的认识**
- “线程数更多”不等于“吞吐更高”。
- 并行程序通常存在一个拐点：
  - 拐点前：增加线程可以提高吞吐
  - 拐点后：增加线程只会扩大调度和同步成本

**以后遇到类似问题时提醒自己**
- 不要把线程数当成单调增益参数。
- 一定要结合任务粒度（grain size）一起分析。

---

### 误区 5：低估了“单全局队列 + 单自旋锁”在高线程数下的扩展性问题

**当时的错误想法**
- 觉得只要队列正确、锁也正确，线程池自然就会随着线程数线性扩展。
- 没充分意识到：所有 worker 都在争同一个热点，会把并行执行重新压缩成串行争用。

**为什么这是错误经验**
- 全局 `tasks` 队列 + 单 `atomic_flag` 自旋锁，会形成一个强热点。
- 线程越多，越多核心同时对同一个 lock cache line 做 test-and-set。
- 结果不是“更多线程更快”，而是：
  - lock contention 上升
  - cache line bouncing 加剧
  - 有效任务时间占比下降

**修正后的认识**
- 对轻量任务，调度器的数据结构本身就是性能核心。
- “共享队列是否成为瓶颈”必须单独分析，不能只看功能正确性。

**以后遇到类似问题时提醒自己**
- 遇到线程数一高就退化时，优先怀疑：
  - 全局锁热点
  - 原子变量热点
  - cache line bouncing
- 不要第一反应只盯业务逻辑。

---

### 误区 6：低估了 per-task `std::function` 封装和入队成本

**当时的错误想法**
- 认为“每个 task 封成一个 lambda 丢进队列”只是写法问题，不会成为主要瓶颈。
- 更关注线程池有没有并行，而不是每个任务被调度前后多付出了多少固定成本。

**为什么这是错误经验**
- 对极轻任务，单个 task 的有效工作可能比调度包装还轻。
- 每个 task 都经历：
  - lambda 捕获
  - `std::function` 构造/移动
  - enqueue push
  - worker pop
- 当 task 本身很小，这些固定成本就会盖过真实计算。

**修正后的认识**
- 对 fine-grained 任务，最应该优化的是“任务分发路径”，而不是只看 worker 数。
- 用共享 `next_task_id.fetch_add(1)` 直接分发 task id，通常比“每个 task 一个 closure”更适合这种实验场景。

**以后遇到类似问题时提醒自己**
- 只要任务粒度很细，就问自己：
  - “我的调度路径是不是比任务本身还贵？”
- 如果答案可能是是的，就该重新审视任务表示方式。

---

### 误区 7：把 busy-spin 的代价想得过轻

**当时的错误想法**
- 觉得 `_mm_pause()` 已经是优化过的自旋，所以空转成本应该不大。
- 没充分重视“空队列时所有 worker 同时自旋”带来的系统级干扰。

**为什么这是错误经验**
- `_mm_pause()` 只是降低自旋伤害，不是把空转变成免费。
- 当很多 worker 在空队列上不断抢锁、失败、pause、再抢时：
  - CPU 会被空闲线程持续占用
  - 真正在做有效工作的线程也会被影响
  - 尾延迟和整体吞吐都会变差

**修正后的认识**
- spinning 方案适合“很快就会有下一份工作”的场景。
- 一旦空闲期变长，sleeping/wakeup 机制才更合理。

**以后遇到类似问题时提醒自己**
- 自旋不是零成本。
- 所有 busy-wait 都要问：
  - 等待时间是不是足够短？
  - 等待线程数量是不是足够少？

---

### 误区 8：把 `ThreadPoolSpinning` 误解成“必须使用 spin lock”

**当时的错误想法**
- 看到类名里有 `Spinning`，就下意识认为实现里必须围绕 `spin lock` 来设计。
- 进一步把“spinning thread pool”和“用 test-and-set 自旋锁保护共享队列”画上了等号。

**为什么这是错误经验**
- `spin lock` 是一种**互斥手段**，它解决的是“谁能进入临界区访问共享状态”。
- `spinning thread pool` 描述的是一种**等待策略**，它强调的是“worker 没活时不睡眠，而是主动轮询等待”。
- 这两个概念有关，但不是同一个层次。
- 因此 `ThreadPoolSpinning` 的核心要求通常是：
  - 线程池常驻复用
  - 空闲时 busy-wait / `_mm_pause()`
  - 不依赖条件变量睡眠
- 它**并不要求**必须有：
  - 全局任务队列
  - `atomic_flag` 自旋锁
  - `queue<std::function<void()>>` 这种任务表示方式

**修正后的认识**
- `Spinning` 约束的是“没活时怎么等”，不是“有活时一定用什么锁”。
- 如果任务分发可以直接用 `atomic<int> next_task_id_` 完成，并且 worker 空闲时仍然通过 `_mm_pause()` 轮询，那么它仍然是一个合法的 `ThreadPoolSpinning` 实现。
- 对这个实验来说，`next_task_id_.fetch_add(1)` 往往比“全局队列 + 单 spin lock”更自然，也更容易避免调度热点。

**以后遇到类似问题时提醒自己**
- 先区分“同步原语”和“等待策略”是不是被我混成一件事了。
- 看到 `spinning` 时，先问自己：
  - 是在说 lock 的实现？
  - 还是在说 worker 空闲时的等待方式？
- 如果一个实现满足“线程池复用 + 空闲不睡眠 + 主动轮询”，即使没有 spin lock，也可能完全符合题意。

---

### 误区 9：以为 `next_task_id_` 解决了任务分发，就自动解决了整批任务的状态同步

**当时的错误想法**
- 一旦改成 `next_task_id_.fetch_add(1)`，就认为 thread pool 的同步问题已经基本解决。
- 没有区分“领取任务编号”和“发布一整批任务元数据”其实是两个不同问题。

**为什么这是错误经验**
- `next_task_id_` 只能保证多个 worker 不会拿到重复的 task id。
- 它不能单独保证 worker 看到的是一组一致的批次状态，例如：
  - `current_runnable`
  - `num_total_tasks_`
  - `remaining_tasks`
  - 当前 batch 是否已发布
- 如果没有单独的批次发布协议，worker 可能看到：
  - 新的 task id 范围
  - 旧的 runnable 指针
  - 或半初始化状态

**修正后的认识**
- `next_task_id_` 解决的是 **work distribution**。
- `batch_active` / 当前 batch 元数据的发布，解决的是 **batch publication**。
- 这两个问题必须分开设计。

**以后遇到类似问题时提醒自己**
- 看到“共享原子计数器”时，先问：
  - 它是在分发 work？
  - 还是在发布状态？
- 不要用一个原子变量去想当然地承担整个状态机的职责。

---

### 误区 10：忽略了构造时初始值的重要性，导致 worker 在线程池启动后读到垃圾状态

**当时的错误想法**
- 觉得成员变量可以等 `run()` 时再写，构造函数里不急着全部初始化。
- 低估了“worker 在线程池创建后就已经开始运行”这一事实。

**为什么这是错误经验**
- worker 线程在构造函数里启动后，会立刻读取共享成员。
- 如果这些成员没有初始化，例如：
  - `batch_active`
  - `current_runnable`
  - `remaining_tasks`
  - `num_total_tasks_`
- 那 worker 就可能基于未定义值进入错误路径，轻则逻辑错，重则直接段错误。

**修正后的认识**
- 线程池里，构造函数不是“只建线程”，而是“先把共享状态初始化成安全空闲态，再启动线程”。
- 安全空闲态至少要保证：
  - 没有 batch 在运行
  - runnable 指针为空
  - 计数器为 0
  - stop 为 false

**以后遇到类似问题时提醒自己**
- 只要 worker 会在构造后立刻跑，就必须先想：
  - 它第一次读到共享状态时应该看到什么？
- 初始值不是形式问题，而是并发正确性的一部分。

---

### 误区 11：局部变量与成员变量同名时，低估了 shadowing 在并发代码里的杀伤力

**当时的错误想法**
- 觉得在 `run()` 里临时再定义一个 `remaining_tasks` 没什么大不了。
- 没立刻意识到主线程和 worker 可能因此在操作两个完全不同的计数器。

**为什么这是错误经验**
- 在并发代码里，状态机依赖的是“多个线程是否在观察同一个共享状态”。
- 如果主线程等待的是局部 `remaining_tasks`，而 worker 递减的是成员 `remaining_tasks`，那么：
  - 主线程和 worker 根本不在协作
  - 轻则死等
  - 重则触发未定义行为或崩溃

**修正后的认识**
- 并发变量一旦承担跨线程协作语义，就必须非常明确它的作用域。
- 共享状态应该尽量只保留一份，不要出现“看起来同名，实际上不同对象”的情况。

**以后遇到类似问题时提醒自己**
- 对所有跨线程共享计数器，检查两件事：
  - 它是不是类成员？
  - 有没有被局部变量遮蔽？
- 在并发代码里，shadowing 不是代码风格问题，而是正确性问题。

---

### 误区 12：把“锁住任务分发入口”误解成“锁住整个并行执行”

**当时的错误想法**
- 看到单个 `spin_lock` 保护共享队列，就以为“无论多少线程也只有一个线程能运行”。
- 把“调度入口串行化”和“任务执行串行化”混为一谈。

**为什么这是错误经验**
- 如果锁只包住：
  - 检查队列
  - pop 一个任务
- 然后在锁外执行 `runTask()`，那么多个线程仍然可以并行计算。
- 真正被串行化的是“谁先领到下一个任务”，而不是“谁能执行任务”。
- 不过当 task 很轻时，这个调度入口就会成为主要瓶颈，看起来近似像“被锁死了”。

**修正后的认识**
- 要区分：
  - **scheduling contention**：大家在争怎么领活
  - **execution parallelism**：拿到活之后能否并行计算
- 当前实现的问题更多是前者，而不是后者。

**以后遇到类似问题时提醒自己**
- 看到单锁时先问：
  - 它锁住的是调度，还是锁住了真正计算？
- 如果计算在锁外，就不要把性能差直接描述成“完全没有并行”。

## 三、实战技巧与检查清单

### 技巧 1：先分清“正确性问题”和“性能问题”

先问自己当前现象属于哪类：
- 段错误 / 死锁 / 漏通知 / 重复执行 / 漏执行 → 正确性问题
- 线程多了反而变慢 / CPU 很高 / 尾延迟大 → 性能问题

不要在正确性没收敛时就急着做性能解释。

---

### 技巧 2：把共享状态按层次分类

实现线程池前，先把变量按语义分成三类：
- **线程生命周期状态**：`stop`
- **批次状态**：`current_runnable`、`num_total_tasks_`、`batch_active`
- **任务分发/完成状态**：`next_task_id_`、`remaining_tasks`

这样更容易发现：哪些变量该在构造时初始化，哪些变量该在每次 `run()` 时重置。

---

### 技巧 3：把等待条件和完成条件分开想

在这类题里，最容易混淆的是：
- task 被“领完”
- task 被“做完”

记住：
- `next_task_id_ >= num_total_tasks` 只说明任务编号基本被领完了
- `remaining_tasks == 0` 才说明整批任务真的完成了

---

### 技巧 4：先问“这是不是本轮状态”

写循环里的变量时，先给它贴标签：
- 线程长期状态？
- 批次状态？
- 单轮临时状态？

像 `has_task` 这种变量，必须是单轮临时状态，每轮重置。

---

### 技巧 5：轻任务先怀疑调度路径，重任务再怀疑计算本身

如果 workload 是 `super_light` / `super_super_light`：
- 优先怀疑任务分发、锁争用、原子热点、busy-spin

如果 workload 是重计算：
- 再去看真正的并行执行效率、负载均衡和核利用率

---

### 技巧 6：看到 segfault，先怀疑“未初始化共享状态”和“悬空/野指针”

尤其在线程池里：
- 构造后 worker 会立刻跑
- 如果 `batch_active`、`current_runnable`、计数器没初始化好
- 很容易在第一次 `run()` 前就炸掉

并发下的 segfault，很多时候不是“算法太复杂”，而是“状态发布太早 / 初始值不安全”。

---

### 技巧 7：最小验证法

每次改完不要只跑 benchmark，先做这几种最小验证：
- `num_total_tasks = 0`
- `num_total_tasks = 1`
- `num_total_tasks < num_threads`
- 连续多次调用 `run()`
- 用数组统计每个 task 是否恰好执行一次

先确认“对”，再确认“快”。

---

## 四、这几次复盘后形成的稳定判断框架

以后分析并发程序时，先按下面顺序判断：

1. **先看正确性**
   - 有没有 data race？
   - 有没有任务重复执行 / 漏执行？
   - 有没有退出协议不完整、死锁、漏通知？

2. **再看锁的保护范围**
   - 锁内是不是只保护共享状态？
   - 有没有把计算放进临界区？

3. **再看任务粒度与调度成本**
   - task 是 heavy 还是 super light？
   - 调度路径会不会比 task 本身更贵？

4. **最后看扩展性瓶颈**
   - 是全局锁热点？
   - 是原子热点？
   - 是 busy-spin？
   - 是 oversubscription / SMT 争抢？

## 四、给以后的自己的一句话

## 五、True Sharing / False Sharing 规则沉淀（新增）
### 规则 1：先判类型再优化
- 先判断是 `true sharing`（同一变量被多线程改）还是 `false sharing`（不同变量落在同一 cache line）。
- 不先判类型就优化，通常会走错方向。
### 规则 2：单原子热点默认按 true sharing 处理
- 像 `next_task_id_.fetch_add(1)` 这类全局发号器，线程数上去后要优先怀疑它是扩展性上限。
- 必做扩展曲线验证：`n=2/4/8/16/32/64`。
### 规则 3：true sharing 优先“降频”，不是先“对齐”
- 对 true sharing，首选减少共享访问频率（批量领任务、分层队列、work stealing）。
- 仅做 padding/align 通常不能解决“同一变量争用”。
### 规则 4：false sharing 优先“改内存布局”
- 对每线程独立计数器/状态使用 `alignas(64)` 或 padding，避免热点写入落在同一 cache line。
- 该类问题改布局通常立竿见影。
### 规则 5：轻任务测试先查调度热点
- 在 `super_light` / `ping_pong_*` 退化时，先查共享原子/锁热点，再查计算逻辑。
- 轻任务里，调度路径常常比任务计算更贵。
### 规则 6：用曲线证据，不凭直觉
- 若性能从 `16 -> 32 -> 64` 改善变小或回退，优先判定为共享热点或调度争用，而非算法错误。
- 先拿曲线，再下结论。
### 规则 7：术语必须精确
- “同一变量争用”叫 true sharing。
- “不同变量同线干扰”才叫 false sharing。
- 复盘里必须写清，避免概念混用导致错误优化。
### 快速检查清单（提交前 1 分钟）
- [ ] 我是否先区分了 true sharing / false sharing？
- [ ] 线程数扩展曲线是否覆盖 `2/4/8/16/32/64`？
- [ ] 若是 true sharing，我是否在做“降频”而不是只做 padding？
- [ ] 若是 false sharing，我是否检查了数据布局与 cache line 对齐？
- [ ] 结论是否由曲线和测试输出支撑，而不是凭感觉？

## 七、考试前速查卡片（可复用）

- `ThreadPoolSpinning` 高线程退化，先判定为 **true sharing（同一原子热点）**，不要先叫 false sharing。
- 典型热点是 `next_task_id_.fetch_add(1)`：线程越多，单发号口争用越重。
- 证据必须看扩展曲线：`n=2/4/8/16/32/64`；后段收益变小或回退即为争用信号。
- 优化优先级固定：**先降频（chunk 领任务） -> 主线程参与执行 -> 参数调优**。
- false sharing 只在“不同变量同 cache line 干扰”时成立，主解法是布局/对齐（`alignas(64)`/padding）。
- 轻任务（`super_light` / `ping_pong_*`）先查调度路径开销，再查计算逻辑。
- 并发分析顺序：**正确性 -> 锁范围 -> 调度成本 -> 扩展性热点**。
- 快测三档：
  - 30秒：`./runtasks -n 16 super_super_light`
  - 2分钟：`./runtasks -n 16 super_light && ./runtasks -n 16 ping_pong_equal`
  - 10分钟：`for n in 2 4 8 16 32 64; do ./runtasks -n $n ping_pong_equal; done`

## 八、ThreadPoolSleeping 本轮沉淀（先正确性）

### 目标是否达成
- [x] 已建立正确方向：`wait` 在锁内、`runTask` 在锁外、完成后回锁内更新计数并通知。
- [ ] 仍需保持发布与边界语义一致（尤其 `num_total_tasks==0` 分支和批次发布原子性）。

### 必修风险点（本轮）
1. **持锁执行任务会把并行退化成串行**
   - 现象：`Parallel + Thread Pool + Sleep` 远慢于 `Spin`，甚至比串行还慢。
   - 修正：锁内只做等待/领任务/状态更新，`runTask` 必须放锁外。
2. **`run()` 批次发布要在同一临界区完成**
   - 风险：`current_runnable`、`num_total_tasks_`、`next_task_id_`、`remaining_tasks`、`batch_active` 分散发布会导致状态机边界不清晰。
   - 修正：一次加锁设置完整 batch 状态，再 `notify_all`。
3. **原子与锁混用会放大心智负担**
   - 结论：若状态已由 `mutex + cv` 管理，可逐步收敛为“锁主导”语义，减少隐式竞态窗口。

### 最小修改顺序（以后照这个做）
1. 先修正确性：锁边界 + 谓词 + 完成通知
2. 再修边界：`num_total_tasks<=0` 直接返回，不发布活动 batch
3. 最后看性能：只在结构稳定后比较 `Sleep` vs `Spin`

### 自测清单（Sleeping 专用）
- [ ] `num_total_tasks = 0`：不挂起、不发布脏 batch
- [ ] `num_total_tasks = 1`：恰好执行一次
- [ ] 连续多次 `run()`：无死锁/漏通知/重复执行
- [ ] `./runtasks -n 16 ping_pong_equal`：Sleep 不应异常慢到数量级退化

## 九、系统性误区清单（概念理解与设计思路）

这部分专门记录“不是代码 typo，而是认知层面的偏差”。后续每次实现前先过一遍。

### 误区 A：把 atomic 理解成“锁住变量”
- **错误理解**：atomic 相当于给变量上锁，别人不能同时动它。
- **正确理解**：atomic 只保证“单变量操作”的原子性和可见性语义，不保证多变量复合状态一致。
- **设计影响**：状态机（发布 batch、完成通知）必须由 `mutex + cv` 承担，不能只靠 atomic 拼凑。

### 误区 B：以为有 mutex 后 atomic 完全没意义
- **错误理解**：既然有锁，atomic 一律可以删除。
- **正确理解**：若所有访问都在同一把锁内，atomic 可简化为普通变量；若存在锁外高频访问，atomic 仍有价值。
- **设计原则**：先确定“锁主导”还是“混合模式”，避免半锁半原子导致心智混乱。

### 误区 C：把“wait 后释放锁”理解成“wait 一返回立刻 unlock”
- **错误理解**：`wait` 返回后立刻释放锁即可。
- **正确理解**：应先在锁内完成一个小事务（判 stop + 领任务 + 拷贝局部状态），再 unlock 去执行重计算。
- **设计原则**：`wait/判定/领任务` 同事务；`runTask` 锁外；完成计数再回锁内。

### 误区 D：认为主线程通知子线程、子线程通知主线程就需要两把锁
- **错误理解**：通信方向不同就要不同的 mutex。
- **正确理解**：一组共享状态应由同一把 mutex 保护；可配两个 cv（`cv_work/cv_done`）表达不同事件。
- **设计原则**：锁是“保护状态一致性”的，不是“按通知方向分配”的。

### 误区 E：忽视 condition_variable 谓词中的 stop 语义
- **错误理解**：`wait` 只等 `batch_active` 就够了。
- **正确理解**：析构路径必须让线程能退出，谓词要包含 `stop`，否则可能唤醒后继续睡回去。
- **设计原则**：任何 worker wait 谓词都先写 `stop || ...`。

### 误区 F：持锁执行 `runTask` 只是“小问题”
- **错误理解**：先保证正确性，暂时持锁跑任务问题不大。
- **正确理解**：这会把并行执行串行化，轻任务下会出现数量级退化（你已实测到 5s 级别退化）。
- **设计原则**：锁内只处理共享状态；计算永远锁外。

### 误区 G：`num_total_tasks == 0` 也照常发布 batch
- **错误理解**：统一流程更简单，0 任务也走完整发布流程。
- **正确理解**：会产生“active 但无任务”的脏状态，可能引入无效唤醒或等待语义漂移。
- **设计原则**：0 任务直接 return，不发布活动 batch。

### 误区 H：把测试慢直接归因于算法差，忽视构建/测量方法
- **错误理解**：结果慢就是实现错。
- **正确理解**：`-O0` 与优化构建差异会极大影响轻任务；harness 全量跑法也会放大体感时间。
- **设计原则**：先确认编译配置、测试维度（单测/子集/全量）再下性能结论。

### 误区 I：混淆 true sharing 与 false sharing
- **错误理解**：高线程退化都叫 false sharing。
- **正确理解**：`next_task_id_.fetch_add(1)` 是 true sharing（同一热点变量）；false sharing 是不同变量同 cache line 干扰。
- **设计原则**：先判类型再优化：true sharing 优先“降频”（chunk 领任务），false sharing 优先“改布局”。

### 误区 J：把等待条件和完成条件混在一起
- **错误理解**：任务编号领完就等价于任务完成。
- **正确理解**：`next_task_id` 只表示“领号进度”，`remaining_tasks==0` 才是“执行完成”。
- **设计原则**：等待谓词与完成谓词分离，避免早返回或假完成。
