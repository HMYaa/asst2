# 在职工程师并发成长复用手册

> 目标：从“完成作业”升级到“可复用工程能力”，把一次 Lab 的收获沉淀为长期资产。

---

## 1. 结论先行

- 你的学习方向是对的：要从“逐题实现”转向“模式抽象 + 经验复用”。
- 但不能跳过实现：模式是从坑里提炼出来的，不是从文档里背出来的。
- 在职人的正确路径是：**小步实现 -> 复盘抽象 -> 场景迁移**。

---

## 2. 核心成长原则（高性能并发场景）

### 原则 1：模式是“坑的抽象”，不是“捷径”

- 只读不写，容易停留在“知道概念”而不是“能诊断问题”。
- 每个关键并发概念至少做一次最小实现和一次故障复现。

建议动作：

1. 写一个最小可运行版本（1-2 小时）。
2. 故意注入一个并发 bug（如去掉谓词、错误通知顺序）。
3. 用证据工具定位（gdb/perf/helgrind）。
4. 形成一条“可执行规则”。

### 原则 2：学习必须锚定真实业务场景

- 每学一个模式，必须回答：“我当前工作里哪个模块会遇到同类问题？”
- 没有场景锚点，知识会快速遗忘。

典型映射：

- `cv.wait(predicate)` -> 消费者阻塞等待/避免空轮询
- 发布协议（先写状态再 notify） -> 配置热更新可见性/初始化发布
- chunk 粒度 -> 线程池吞吐与 tail latency 折中
- DAG 依赖传播 -> 数据流水线/任务编排引擎

### 原则 3：成长分水岭是“问题分类能力”

- 高手先分类后解题，不是看到现象就改代码。
- 并发问题建议先落入以下四象限再排查：

1. 数据竞争（race）
2. 原子性缺失（check-then-act）
3. 漏通知/伪唤醒（wait-notify 协议错误）
4. 死锁/活锁/空转（等待条件与推进条件不匹配）

---

## 3. 可复用工程模板（每个并发模块都写）

每次设计线程池、调度器、异步执行器，先补这 1 页“设计卡”：

1. **API 契约**
   - 同步/异步语义是什么？
   - 返回时保证什么完成条件？
2. **状态变量所有权**
   - 谁写、谁读、在哪把锁下、是否 atomic？
3. **等待条件 vs 完成条件**
   - `wait` 的谓词是什么？
   - 谁负责 `notify`，何时发？
4. **生命周期协议**
   - 构造、运行、停止、析构顺序是否闭合？
5. **失败模式清单**
   - 死锁、漏通知、忙等、尾延迟、资源泄漏
6. **验证计划**
   - 功能正确性 + 压测 + 边界条件（0/1/突发任务）

---

## 4. 并发代码 Review 最小清单（提交前必查）

- `condition_variable::wait` 是否都带谓词？
- `notify` 前共享状态是否已完整发布？
- 是否有“等待条件”和“完成条件”混淆？
- 析构是否“先 stop -> 再 notify -> 再 join”？
- 是否存在无意义自旋导致 CPU 空转？
- chunk 粒度是否过大引发负载不均？
- 关键路径是否有可观测指标（队列深度、等待时长、任务完成率）？

---

## 5. 在职人成长节奏（8 周可执行版）

### 第 1-2 周：夯实正确性

- 目标：避免 data race、死锁、漏通知。
- 输出：并发问题分类卡 + 10 条 review checklist。

### 第 3-4 周：建立性能诊断能力

- 目标：从“猜性能”转到“证据驱动”。
- 输出：常用诊断命令模板（perf/gdb/火焰图）与案例。

### 第 5-6 周：沉淀复用组件

- 目标：把线程池/调度器封装成团队可复用骨架。
- 输出：统一生命周期协议 + 可配置策略（spinning/sleeping/chunk）。

### 第 7-8 周：场景迁移与复盘

- 目标：把 Lab 模式迁移到真实业务（如 RDMA/NCCL/任务编排）。
- 输出：一份“生产问题 -> 证据 -> 修正 -> 规则”的复盘文档。

---

## 6. 一句话行动指南

- 先正确性，后性能。
- 先证据，后优化。
- 先复盘，后抽象。
- 每次学习都要产出可复用资产（清单、模板、脚手架、排障手册）。
